# recruit_match

**A standalone, evidence-oriented recruitment search and job-matching pipeline.**

`recruit_match` discovers public job-posting candidates, preserves source provenance, and supports a staged workflow for reviewing posting evidence and evaluating job fit. Search discovery is not the same as official verification: results may be incomplete, stale, or unverified.

## Features

- Configurable public search-provider adapter and optional policy-bounded HTML discovery adapter
- Query planning and multi-platform search orchestration
- Source-artifact provenance and explicit execution-status reporting
- Evidence-linked job-fit evaluation for selected postings
- Unit tests and GitHub Actions validation workflow

## Requirements

- Python 3.10 or newer
- Python standard library for the core pipeline
- An approved search API endpoint, API key, and exact host allowlist for public-search API calls
- Optional reviewed crawl configuration for HTML discovery

## Quick start

Clone the repository and inspect the command-line options:

```bash
git clone https://github.com/ydonchoi/recruit_match.git
cd recruit_match
python run_pipeline.py --help
```

Example search request:

```bash
python run_pipeline.py \
  --iteration 1 \
  --request "education administration, research support, and policy research jobs" \
  --axis "education administration" \
  --axis "research support" \
  --axis "policy research" \
  --query-limit 10
```

The default search adapter requires explicit provider configuration. Without it, the pipeline reports a blocked or partial run rather than treating missing configuration as zero results.

## Configure a public search provider

Set the provider endpoint, API key, and exact allowed host through environment variables. Do not commit credentials.

```bash
export RECRUIT_MATCH_SEARCH_ENDPOINT="https://your-approved-provider.example/v7/search"
export RECRUIT_MATCH_SEARCH_API_KEY="provide-the-key-securely"
export RECRUIT_MATCH_SEARCH_ALLOWED_HOSTS="your-approved-provider.example"
python run_pipeline.py --request "research support jobs" --query-limit 10
```

The provider must return a JSON response compatible with a `webPages.value` array containing `url`, `name`, and `snippet` fields. Provider-specific response formats require a dedicated parser.

## Optional HTML discovery

The HTML crawler is discovery-only and must be explicitly configured with reviewed seed URLs, allowed hosts, and terms review status. Review each target site's policies and access conditions before enabling crawling. The example below illustrates the configuration shape only; it does not establish that the URL or host is suitable for real use.

Set `RECRUIT_MATCH_CRAWL_CONFIG_JSON` to a JSON array such as:

```json
[
  {
    "platform": "KEDI",
    "seed_urls": ["https://www.kedi.re.kr/"],
    "allowed_hosts": ["www.kedi.re.kr", "kedi.re.kr"],
    "terms_reviewed": true,
    "request_delay_seconds": 2,
    "max_links_per_seed": 100
  }
]
```

Do not set `terms_reviewed` to `true` until a responsible operator has reviewed the relevant terms. The crawler applies host and protocol restrictions and respects `robots.txt`; it is not designed to bypass access controls.

## Workflow

1. **Discover:** search configured platforms and collect public posting candidates.
2. **Verify and analyze:** use the separately configured verification service and source evidence to assess posting details.
3. **Evaluate fit:** select postings for evidence-linked job-fit assessment.

The later stages depend on available evidence and configured services. A discovered URL alone does not establish that a posting is official, open, or that an applicant is eligible.

For workflow and evidence boundaries, see:
- [Mandatory search workflow](docs/mandatory-search-workflow.md)
- [Requirement-centered job matching](docs/requirement-centered-job-matching.md)
- [Target workflow design](docs/target-workflow-design.md)

## Privacy and data handling

- Do not enter applicant names, contact details, credentials, or other directly identifying or sensitive data into search requests.
- Keep API keys in environment variables or an appropriate secret manager. Never commit live secrets.
- Inspect generated logs, data, and source artifacts before sharing them.
- Local runtime files and artifacts may contain operational or job-related information; do not assume they are safe for publication merely because they are generated by the application.
- See `.gitignore` for patterns excluded from version control. Ignoring a file does not remove it from existing commits.

## Development and tests

Run the validation checks locally:

```bash
python -m compileall -q run_pipeline.py search_engine.py search_orchestrator.py analysis_pipeline.py workflow_session.py interactive_workflow.py adapters tests
python -m unittest discover -s tests -v
python -m unittest discover -s tests -p "test_runtime_integration.py" -v
```

The repository includes a GitHub Actions workflow that runs compilation, unit tests, integration tests, and a fail-closed CLI check. A successful workflow run should be confirmed in the Actions tab; the existence of a workflow file does not mean the current revision passes.
